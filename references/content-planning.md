# 内容规划规则

本文件将输入长文拆为“原文理解”和“营销表达”两层。它们必须先完成并得到确认，才进入配方、资产和版式。

## 1. 生产前判断顺序

| 顺序 | 先判断什么 | 通过条件 | 未通过时 |
|---|---|---|---|
| 1. 输入可用性 | 原文、素材、事实和限制是否齐全 | 只盘点本次对话明确提供的输入；每条源信息可追溯 | `input-blocked`，补输入或确认歧义 |
| 2. 内容分析 | 文案包含哪些主张、解释、证据、利益与行动 | 每条内容已标记角色与真实关系 | 回到原文整理，不编造关系 |
| 3. 营销分析 | 海报先讲什么、强调什么、行动如何出现 | 已产出展示文案，并把原文事实逐项映射到展示内容 | `awaiting-copy-confirmation` |
| 4. 首帧策略 | 是否存在并使用导师 / 嘉宾人像 | 文案已确认；人像问题已回答，内部路线已确定 | `awaiting-hero-confirmation` |
| 5. 整图叙事 | 全文最主要的阅读关系 | 已选 `Rxx` 与阅读区序列 | 重组内容，不缩字 |
| 6. 阅读区与资产 | 每段关系、L 契约、资产是否可用 | 每区有签名、契约和资产职责 | 改结构、补素材或删去无意义装饰 |
| 7. 放行 | 是否能实际生产 | 所有阻塞关闭 | `approved-for-production` |

用户先只确认展示文案。文案确认后，才按“是否有导师人像 / 是否放在首帧”的自然语言问题完成首帧判断；不得要求用户确认或理解 `mentor-portrait`、`imagegen` 等内部技术路线。原文事实不是可选项：它们默认冻结，只有输入本身含糊或缺失时才向用户提问。R 配方、阅读区顺序、L 契约、长图结构和视觉方向由 Agent 依据真实信息关系选择；除非用户主动询问，不要把内部版式或视觉判断变成问卷。

### 输入白名单与基线隔离

- 将本次用户明确提供的文案、附件、链接和指定路径写为 `current_input_allowlist`。只有这份白名单中的真实素材可以进入资产表。
- 不得通过 `find`、`rg --files`、目录浏览或其他扫描盘点当前工作目录、上级目录、历史案例、旧输出或参考图库。它们不是本次输入。
- Skill 内 `assets/baseline/` 仅是批准质量样张：可以按固定路由阅读其说明和指定示例，以校准黑金视觉语言；不得将其列入 `current_input_allowlist`、资产表或素材缺口报告。
- 用户没有明确输出目录时，确认稿只在对话和 `plan.md` 中准备；不得根据当前工作目录猜测输出位置。

## 2. 内容分析：理解原文，不改原文

保留完整 `source_copy`，并把每个源模块标为：

- `claim`：核心主张；
- `context`：对象、背景或副标题；
- `explain`：解释、并列观点；
- `proof`：数据、案例、资源、人物身份或截图；
- `benefit`：权益、结果、价值或覆盖范围；
- `action`：时间、价格、二维码或行动。

同时列出 `fact_locks`。它不是一小份待确认清单，而是原文中**全部事实性陈述**的映射表：人名、机构、品牌、产品、日期、时间、地点、金额、数量、课次、权益、CTA、二维码动作、经历、成果、覆盖范围及任何可验证主张都必须保留原意。每条 `display_copy` 必须记录来源模块 ID；不能从原文推出的结论不得写进海报。

先识别真实关系，再选择 `Lxx`：并列、顺序、进阶、比较、层级、真实证据、权益/交付、行动或无结构化关系。没有真实关系时，用正文或平级结构，不伪造时间轴、流程、对照、Logo 或箭头。

## 3. 营销分析：生成待确认的展示文案

在不改变 `fact_locks` 的前提下，生成：

```text
Hero Message：海报最重要的一句话
Supporting Message：帮助理解主张的一句话
Proof：可信度、数据、案例或人物依据
Benefits：读者获得什么
CTA：读者下一步做什么
Display Copy：分配到各阅读区的精简展示文字
```

展示文案可以合并重复句、提炼标题、调整阅读顺序和缩短说明；每一条必须能回溯到 `source_copy`，且不能改变、弱化或夸大原始事实。用户确认的是“这样提炼和表达是否准确、营销重点是否正确”，不是确认事实是否应该保留。确认前不得生产图片或整图。

### 展示文案的确认与修订

给用户的确认稿只能包含：项目、主标题、副标题、重点内容、报名/行动信息，以及一句“请确认；如需修改，直接指出要改的内容”。不展示内部结构、视觉方向或技术实现。

- 用户确认：记录 `copy_status=confirmed`，进入首帧人像判断。
- 用户要求修改：记录 `copy_status=revision-requested` 与修改意见；回到本节重写 `display_copy`，保留 `source_copy` 和全部 `fact_locks`，再发新的精简确认稿。
- 修订循环中不得启动首帧生图、处理人像、排版、创建生产文件或导出。只有新版本展示文案被确认，才离开本节。

### 首帧人像判断（文案确认后）

1. 当前输入没有导师 / 嘉宾人像：只问“是否有希望放在海报首帧展示的导师或嘉宾人像可提供？”用户回答没有后，内部设为 `hero.strategy=imagegen`，不再追问技术方案。
2. 当前输入已有导师 / 嘉宾人像：只问“是否将这张 / 这组导师人像放在海报首帧，作为主视觉呈现？”回答是则内部设为 `mentor-portrait`；回答否则设为 `imagegen`。
3. 用户要求补充或替换人像：保持 `awaiting-hero-confirmation`，等待素材；不创建生产资产或先行排版。

## 4. 阅读区签名与连续节奏

每个阅读区记录：

```text
reader_question：读者此刻需要确认什么
claim：本段建立的结论
evidence_role：文字解释 / 已确认事实或数据 / 真实来源资产 / 语义主视觉 / 程序化结构 / 阅读承诺 / 行动引导
visual_relation：文字、主体、证据或结构如何共同解释 claim
Lxx / variant：由真实信息关系选择的契约与变体
intrinsic_height：由正式字体和内容决定的预计高度
transition_to_next：下一阅读区继续回答什么
```

阅读区是连续画布中的内容段，不是 9:16、3:4 或任何固定高度的帧。内容多时优先扩高、拆区、改结构；不得缩小字号、吃掉必要边距或以无意义装饰填空。

相邻阅读区不得重复同一 `Lxx`；同一 `Lxx` 默认最多两次。若同类关系超过上限，遵循 `layout-contracts.md` 的合法降级路径，而不是强行缩字。

## 5. 图像与 icon 判断

首帧策略见 `black-gold-system.md`。中段图像只有在能解释本段关系时才存在。

纯文字分条确有快速区分收益时，可为每条配置一个由关键词导出的 icon。优先许可明确且同一视觉语言的图标库；图标库无法表达且收益明确时，才生成一次无文字、透明背景的同组 icon。加号、方框、菱形等基础形状不算语义 icon，除非原文就是该形状。

